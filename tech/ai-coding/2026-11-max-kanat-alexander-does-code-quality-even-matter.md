> **一句话**：代码质量只为两件事服务——**理解系统**、**安全地修改系统**；AI 让"一次性软件"数量暴涨，这类软件不需要代码质量，但**持久软件**依然需要，而且应该想办法把"严格"变便宜。

## TL;DR

1. 代码质量没有独立目的，**只有两个目的**：让人理解系统在做什么；让人能正确、安全地修改它。debugger、可观测性、eval、测试，全都服务于这两件事。
2. 任何一次修改都有**两类风险**：当下引入问题；让以后的修改更难。后者反过来加剧前者，形成**非线性复合的恶性循环**，最终系统会烂到"每次改动都出问题"甚至"改不动"。
3. AI 正在催生**一次性软件（disposable software）**：失败后果极小、依赖极少、替换只要几小时、维护成本近乎为零。对这类软件，**代码质量不重要**——因为要防的长期风险根本不存在。
4. **持久软件（durable software）**不会消失，绝对数量还会增加。软件是一条"可抛弃 ↔ 持久"的光谱，落在哪一端由四件事决定：**失败后果、替换成本、依赖数量、维护成本**。
5. 除了判断"该投入多少严格度"，还有第二条轴：**降低严格的成本**。手段包括标准化（消除可能性）、in-workflow 工具（自动发生、快、假阳性低）、把测试基础设施做成基础设施（如 in-memory fake）、把 lint 严格度一次开到最大。
6. 三个问题的答案：一次性软件要代码质量吗？——**不要**；持久软件要吗？——**要**；它必须很贵吗？——**不必须**。

## 一、为什么曾经需要代码质量？

### 1.1 一切软件成功都只取决于两个因素

> "Everything you want to ever accomplish with a piece of software depends on two factors and two factors alone: **understanding and executing on that understanding**."

- 无论是调模型、扩系统、推采用率，最终都落在这两件事上。
- 这也是为什么要有 debugger、可观测性、eval、测试——它们存在的根本理由，是提升"理解"或"基于理解执行"的能力。
- 代码质量领域过去几十年的一切实践，**只为这两件事**存在，不是为"正确性"本身，也不是为别的什么。

### 1.2 工程师最重要的两个理解

1. **系统的实际行为是什么？** 不是文档写的行为，是它真正在做的行为。
2. **我怎样才能正确、安全地修改这个行为？**

### 1.3 从 Hello World 到 Chromium：结构才是代码存在的理由

- 一个打印 Hello World 的小程序：我直接告诉你它做什么（"它打印 Hello World"），你说"我要打印 Hi World"，改起来几乎没有理解成本。
- 但真实系统极其复杂。**Chromium** 的代码图（现场展示的真实依赖图）里，组件之间的交互方式近乎无限，**没人能用语言描述整个 Chromium 的行为**；但可以描述**组件**——比如 URL parser 的每个函数做什么。
- 两段都能打印 Hello World 的代码：左边有 Hello World 的**身份与结构**，右边只是一串没有身份、无法辨认的指令。放在几百万行、几十亿行的尺度上，后者根本无法 grok。
- 过去我们谈可读性、可测试性这些"人类概念"，但**真正一直重要的是：系统有没有可理解的结构**。而结构在什么时候最重要？——**要修改系统的时候**（即第二个理解）。

> "The whole reason that we have code at all in the first place is for structure."

## 二、代码复杂性的真正风险

### 2.1 每次修改都携带两类风险

| 风险 | 内容 |
| --- | --- |
| **当下风险** | 引入某种问题——不只是 bug，还包括：行为不符合用户预期、项目大幅延期、预算超支、上线失败等 |
| **未来风险** | 让后续修改变得更难——实质是提高了系统未来出问题的概率 |

两类风险都源自**理解问题**：

- 当下风险 ← 一开始就不容易理解这个系统；
- 未来风险 ← 这次修改让系统**更难被理解**。

### 2.2 所有事故复盘都落在这两条上

> "I can reduce every postmortem I have ever read for any incident to these two factors."

- 生产配置太难理解；
- 有人做了个没人能理解的东西；
- 系统出现了无法理解的涌现行为（emergent properties）。

### 2.3 恶性循环是非线性复合的

- 第二类风险会反哺第一类风险：**理解难度不是线性增长的，而是随时间复合增长**。
- 所有系统最终都会走到一个点：**每一次修改都伴随着某种问题**。
- 有些系统会走到"根本改不动"：上亿行、五亿行的巨型遗留系统，改动必然出事——这在组织、排期、人事上都能看到症状。
- 关于"未来模型能否理解任意复杂度"的争论，讲者的态度是：**也许可以，但今天不用讨论**，因为模型眼下正在做另一件更有意思的事——创造一种新软件。

## 三、AI 催生"一次性软件"

### 3.1 定义：可抛弃的软件

> "This category has always existed. But it's about to become 100,000 times more common than any other form of software. And that is disposable software."

想象一个世界：

- 系统失败几乎没有后果，或压根没有后果；
- 依赖它的人极少；
- 几乎没有其他系统依赖它；
- 变更管理极少甚至不存在；
- 替换成本趋近于零——几个小时、几天就能重写；
- 维护成本基本为零。

**在这个世界里，代码质量不重要。** 因为代码质量要防的是"随时间复合的风险"，而这类软件可能**根本没有"长期"需要保护**。

例子：给某一个人用的计算器、为一次孩子生日派对写的策划软件——用完就扔。

### 3.2 对照：持久软件

| 维度 | 一次性软件（disposable） | 持久软件（durable） |
| --- | --- | --- |
| 生命周期 | 小时 / 天 | 年 |
| 依赖者 | 少数人、几乎没有系统 | 数百万人 / 大量系统 |
| 失败后果 | 极小 / 无 | 可能业务灾难级 |
| 替换成本 | 趋近于零 | 极高 |
| 维护成本 | 近乎免费 | 巨大 |
| 需要的代码质量 | **不重要** | **非常重要** |

- 世界上大多数软件工程师的大部分时间，都在维护这些巨型持久系统。
- 讲者预期：**持久系统会继续存在，而且大概率是世界上最关键的系统，数量还会增加**（AI 让造持久软件也变容易了）。
- 但**数量最多的一定是一次性软件**：几小时可替换、少数人依赖、维护免费，不满意就让 agent 再生成一个。

### 3.3 光谱，而非黑白

> "In the future, we will apply engineering rigor to the degree of disposability of the software."

- 光谱左端：所有工程严格度的实践都不重要；
- 光谱右端：过去几十年积累的工程实践全部重要；
- 定位方法就是四件事：**失败后果、替换成本、依赖数量、维护成本**。都低 → 一次性；都高 → 持久。
- 经验法则：**往"更持久"的方向估**（err on the side of durable）——任何写久了软件的人都会告诉你，这些因素往往比你预期的高。

## 四、哪些软件可以用完就扔？如何主动提高"可抛弃性"

讲者提出一个反直觉的观点：**除了被动画到光谱的某一端，还可以主动把软件做得更可抛弃**。这是软件工程的一个**新学科**：

### 4.1 四种做法

1. **隔离的运行环境**：只能部署到只访问自己数据的环境，禁止接触客户数据、PII 等。
2. **强制独立性**：禁止其他生产系统向这个系统发起入站 API 调用。部署到该环境的东西天然就是可抛弃的。
3. **冗余**：保留一个又老又笨但可靠、难用的备份系统。大家想 vibe code 自己的高效前端就去写，写崩了也无所谓——因为旧系统还在。
4. **限制范围**：只服务一个人、只办一场活动。

> 过去我们问"如何让持久系统更严格"，新问题是"**如何让系统更可抛弃、允许人们把它扔掉**"。

### 4.2 两个常见误解

- **误解一：持久软件工程要消失了。** 不会。反而是 AI 让持久软件的绝对数量增加。
- **误解二：一次性 / 持久是标签。** 不是。它是光谱，变化的是你要投入多少严格度——既包括当下的努力，也包括长期的努力。而且，**你今天很可能判断错**（以为是玩具，结果成了核心系统）。

## 五、AI 时代如何降低质量成本

既然判断会错，最稳的策略不是赌对，而是**把严格变便宜**：

> "If rigor is cheaper, the less you have to worry about where you are on the scale."

严格越便宜 → 越不担心自己站在光谱哪里 → 判断错了（以为一次性、后来变持久）也很容易补救。

### 5.1 标准化：消除可能性

- 为什么标准化？不是为了"老板要求"，而是**消除可能性**。
- 如果没有 PHP，你就不需要研究 PHP 的所有 linter、实践、安全漏洞修复方案。
- 框架、协议同理：支持的前端/后端框架越多、RPC 协议越多，严格就**越贵**——每次都要重新适配。
- 严格当然仍然可能，agent 甚至能每次现场给你造出工具，但**每次都要做一遍**。

### 5.2 in-workflow 工具：默认发生

定义：**不需要程序员主动选择运行、不需要理解它怎么运行，它自己就发生了**的工具。

- 必须**可靠**（假阳性足够低）、**快**、**近乎免费**；
- 因为近乎免费，所以连一次性软件也能用上；
- 本质是把质量成本摊进日常流程，而不是靠人的自觉。

### 5.3 让测试变容易：把测试做成基础设施

- 重点不是"如何写出更好的测试"，而是"**如何让所有人都能不成为测试专家，也得到快且确定性的测试**"。
- 需要大量测试基础设施投入。讲者举了自己做测试负责人时的梦想：**每个服务都提供 in-memory fake 版本**，测试直接用。
- 这件事以前成本高，**现在 coding agent 可以直接帮你生成**；但仍需要有人**决定去做**，并把它共享给所有人。
- 观点：AI 的杠杆不在于让人写更多代码，而在于把过去"值得做但没人力做"的基础设施补齐。

### 5.4 最大严格度：lint 全开

- 把所有 lint 规则开到最大、永不妥协。
- 逻辑和标准化一样：**消除大量讨论**。有人会说"这条规则本身不对"，但只要假阳性率够低、不会造成灾难性后果，就值得——因为你省掉了未来无数个 lint 错误和争论。
- 反例教训：在一百万行的代码库里，突然想开启 lint，结果产生十万行的改动。**一开始就统一开启，比事后补便宜得多**。

### 5.5 讲者没展开的部分

> "I could literally stand here and talk to you about this straight for 10 hours."

降低严格成本还有很多手段；这一场只讲了四个方向，本身就是一个值得单独研究的工程学科。

## 结论：三问三答

| 问题 | 回答 |
| --- | --- |
| 一次性软件需要代码质量吗？ | **不需要** |
| 持久软件需要代码质量吗？ | **需要** |
| 代码质量必须很贵吗？ | **不必须** |

> "For disposable software, no. For durable software, yes. And does it have to be expensive? No."

## 关键概念表

| 英文 | 中文 | 含义 |
| --- | --- | --- |
| disposable software | 一次性软件 | 失败后果小、依赖少、替换便宜、维护近乎免费的软件 |
| durable software | 持久软件 | 生命周期长、依赖多、失败后果严重、维护成本高的软件 |
| engineering rigor | 工程严格度 | 测试、评审、规范等一整套为保证质量而付出的努力 |
| compounding risk | 复合风险 | 每次改动都在降低可理解性，风险随时间非线性累积 |
| in-workflow tooling | 流程内工具 | 无需主动选择、自动运行、快且可靠的检查工具 |
| in-memory fake | 内存假服务 | 用于替代真实依赖、让测试快且确定的基础设施 |
| err on the side of durable | 往持久侧估 | 判断不确定时，假设软件比预想更重要、更长期 |

## 金句（原文 + 译文）

1. **"Everything you want to ever accomplish with a piece of software depends on two factors and two factors alone: understanding and executing on that understanding."**
   → 你想用软件达成的一切，都只取决于两个因素：理解，以及基于理解去执行。

2. **"The whole reason that we have code at all in the first place is for structure."**
   → 我们之所以需要代码，根本原因就是为了结构。

3. **"I can reduce every postmortem I have ever read for any incident to these two factors."**
   → 我读过的每一份事故复盘，都能归因到这两类问题。

4. **"In that world, code quality does not matter."**
   → 在那个世界（一次性软件）里，代码质量不重要。

5. **"We can make software more disposable."**
   → 我们可以主动让软件变得更可抛弃。

6. **"If rigor is cheaper, the less you have to worry about where you are on the scale."**
   → 严格越便宜，你就越不需要担心自己站在光谱的哪一端。

## 我的思考（个人观点，非讲者原意）

1. **这是一套"决策框架"，不是立场。** 网上争论"AI 时代还要不要代码质量"时，双方其实在说不同光谱位置的软件。先问四件事（失败后果 / 替换成本 / 依赖数 / 维护成本），争论会自动消解一半。
2. **AI 让"判断错误"的代价变小，但没让"判断"本身消失。** 讲者说严格要变便宜，本质是承认我们判断不准；工程上最划算的动作往往是把可逆性做大，而不是把预测做准。
3. **"降低严格成本"比"提高严格程度"更值得投入。** 传统工程质量工作喜欢加规则、加流程；这套框架提醒：真正的杠杆在标准化（减少可能性）、默认工具（不需要人记得）、测试基础设施（让正确成为默认路径）。
4. **对个人项目的映射**：个人脚本 / 一次性分析 → 允许烂；会被反复使用、别人依赖的工具 → 一开始就上 lint 全开 + 类型 + CI，因为事后补最贵。
5. **与 Matt Pocock 那场的关系**：Max 回答"**该投入多少严格度**"，Matt 回答"**严格度具体怎么落地成刹车系统**"（自动化检查 → 自动化评审 → 人工评审）。两场连起来看，正好是一套完整的 AI 时代工程质量方法论，见 [另一篇笔记](./2026-11-matt-pocock-why-software-fundamentals-still-matter.md)。
